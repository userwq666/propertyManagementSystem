# 物业管理系统 — 系统设计

## 1. 总体架构

系统采用前后端分离架构：

```
┌───────────────────────────────┐
│         浏览器（Vue 3 SPA）      │
│  Element Plus / ECharts / WebSocket │
└──────────────┬────────────────┘
               │ HTTP(RESTful) / WebSocket
┌──────────────▼────────────────┐
│        Spring Boot 后端        │
│   Controller → Service → Mapper │
│   Security/JWT  RBAC 权限校验    │
│   定时任务     WebSocket 推送    │
└──────────────┬────────────────┘
               │ JDBC
┌──────────────▼────────────────┐
│           MySQL 8.0           │
│     property_management_system │
└───────────────────────────────┘
```

- 前端：Vue 3 + Vite + Element Plus + Pinia + Vue Router + ECharts；
- 后端：Spring Boot 4.0.7 + Spring Security + MyBatis-Plus + MySQL；
- 通信：RESTful JSON 接口 + WebSocket 实时推送；
- 构建部署：Maven 打包，前端构建产物输出到后端静态资源目录，单 JAR 部署。

## 2. 后端分层设计

后端按业务模块分包，模块内统一分层：

```
src/main/java/com/lsy/propertymanagementsystem/
├── common/                 # 公共能力
│   ├── result/             # 统一响应封装
│   ├── exception/          # 业务异常与全局异常处理
│   └── utils/              # JWT、密码、安全工具
├── config/                 # 安全、JWT、Web MVC、MyBatis-Plus、数据库初始化
├── interceptor/            # JWT 认证过滤器
├── task/                   # 定时任务
├── websocket/              # WebSocket 配置、会话管理、消息推送
└── module/                 # 业务模块
    ├── system/             # 认证与系统管理
    ├── community/          # 小区基础
    ├── fee/                # 收费管理
    ├── repair/             # 报修管理
    ├── complaint/          # 投诉建议
    ├── equipment/          # 设备管理
    ├── inspection/         # 巡检管理
    ├── announcement/       # 公告通知
    └── statistics/         # 统计分析
```

每个业务模块内部划分为：

| 包 | 职责 |
|----|------|
| controller | 接收 HTTP 请求，参数校验，返回统一响应 |
| service / impl | 业务逻辑，事务控制，状态流转 |
| mapper | MyBatis-Plus 数据访问接口 |
| domain | 数据库实体 |
| dto | 请求/响应数据传输对象 |
| enums | 状态与类型枚举 |

调用链约定为 `Controller → Service → Mapper → Domain`，禁止 Controller 直接访问 Mapper。

## 3. 权限设计（RBAC）

### 3.1 权限模型

```
用户（sys_user） ──┬── 角色（sys_role） ──┬── 菜单/按钮（sys_menu）
                  │                      └── 权限标识 perms
                  └── sys_user_role 关联
```

- 一个用户可拥有多个角色（当前业务为单角色），一个角色拥有多个菜单/按钮权限；
- 权限标识格式为 `模块:功能:操作`，例如 `repair:record:process`、`fee:expense:audit`；
- 前端通过 `v-permission` 指令控制按钮显隐，后端通过 `@PreAuthorize("hasAuthority('xxx')")` 做接口级校验，双重防护；
- 数据级隔离通过当前登录用户角色/ID 实现：业主只能查看自己的房屋、车位、账单、工单与投诉。

### 3.2 角色与权限分配（初始化固化）

| 角色 | 主要权限范围 |
|------|--------------|
| 超级管理员 | 全部菜单与按钮权限 |
| 物业管理员 | 系统管理、社区管理、收费管理、报修、投诉、设备、巡检、公告、统计全部 |
| 业主 | 楼栋/房屋/车位查看、收费记录、报修（新增/编辑/删除/评价）、投诉、公告、设备记录、费用统计、待办事项 |
| 维修工 | 报修工单（查看/新增/处理/评价）、消费事项（申报/编辑）、投诉、设备记录、维修统计 |
| 巡检员 | 设备台账/记录、巡检计划/记录、报修（查看/新增）、投诉、设备与巡检统计 |
| 财务 | 收费项目/通知/记录、消费事项审核、房屋/业主查看、费用与维修统计 |

> 初始化脚本 `01_system.sql` 已固化全部角色-菜单分配，可通过"系统管理 → 角色管理 → 菜单分配"调整。

## 4. 认证与安全设计

### 4.1 JWT 认证流程

1. 用户登录，后端校验 BCrypt 密码，生成 JWT 并返回 Token、角色、权限集合；
2. 前端将 Token 存于本地，请求时携带 `Authorization: Bearer <token>`；每个标签页在内存生成 `tabId`，并通过 `X-Tab-Id` 请求头/WebSocket 参数传递；
3. 后端 `JwtAuthenticationFilter` 解析 Token，将用户 ID、角色、权限写入上下文；
4. 接口通过 `@PreAuthorize` 或权限校验工具判断是否放行；
5. 登出时将当前 `token + tabId` 加入黑名单，仅失效当前标签页会话；定时清理过期黑名单。

### 4.2 密码安全

- 密码使用 BCrypt 算法加密存储，禁止明文；
- 默认初始密码统一为 `123456`，交付前建议修改。

### 4.3 统一响应与异常

- 所有接口返回统一结构 `Result{ code, msg, data }`；
- 业务异常（`BusinessException`）、参数校验异常、系统异常由全局处理器统一转换，避免堆栈泄漏。

## 5. 实时推送设计（WebSocket）

### 5.1 连接管理

- 前端登录后建立 `ws://host/ws?token=<jwt>` 连接，握手时校验 Token；
- 后端按用户 ID 维护多会话集合，同一账号多端登录均可收到消息；
- 断线后前端每 5 秒自动重连。

### 5.2 推送消息格式

```json
{
  "type": "repair",
  "title": "新派单",
  "content": "有新的报修工单等待处理：BX...",
  "refId": 12,
  "time": 1754000000000
}
```

### 5.3 推送场景

| type | 场景 |
|------|------|
| repair | 新报修、派单/接单、结单、取消、评价、超时自动完成 |
| complaint | 新投诉、受理、处理、回复、确认、评价、撤销 |
| fee | 收费项目发布/启停、缴费确认、账单逾期、消费事项审核、缴费通知发布 |
| inspection | 新计划、计划启停、新任务、任务接单、记录更新、计划完成、巡检异常 |
| announcement | 公告发布、下线、定时发布 |
| equipment | 设备状态变更（故障/维修中/恢复正常） |
| system | 账号启用/禁用 |

### 5.4 列表实时刷新

- 前端收到任意推送后广播 `pms:data-changed` 全局事件；
- 各列表页面订阅该事件并自动重新拉取（200ms 防抖）；
- 任意写接口（POST/PUT/DELETE）成功后同样触发刷新，保证操作者本人页面即时更新。

## 6. 定时任务设计

| 任务 | 执行时间 | 说明 |
|------|----------|------|
| 逾期缴费标记 | 每日 01:00 | 将到期未缴账单标记为逾期 |
| 巡检记录按周期生成 | 每日 02:00 | 按计划频次生成当日巡检任务，一次性计划完成后自动停用 |
| Token 黑名单清理 | 每日 03:00 | 清理过期 Token 黑名单 |
| 报修超时自动完成 | 每小时 | 结单后 24 小时未确认评价的工单自动完成 |
| 公告定时发布 | 每 5 分钟 | 到预约时间的草稿公告自动发布 |

## 7. 核心业务流程设计

### 7.1 报修流程

```
业主/巡检员提交报修（待派单）
  → 管理员派单 或 维修工抢单（处理中）
  → 维修工结单（待确认，可申报消费事项）
  → 报修人确认评价（已完成）
```

设备联动：报修关联设备时，提交报修设备置为"故障"，派单后置为"维修中"，结单后恢复"正常"。

### 7.2 收费流程

```
管理员新增收费项目（物业费，设置单价与通知范围）
  → 发布项目：按范围（全体/楼栋/房屋/业主）自动生成待缴费账单 + 同步生成收费通知
  → 财务线下收款后"填报"实缴金额与备注（已缴费/部分缴费）
  → 业主随时查看自己的账单
```

### 7.3 巡检流程

```
管理员制定巡检计划（周期、设备、指定巡检员）
  → 系统按周期生成巡检记录（二维打卡矩阵：行=设备，列=周期）
  → 巡检员打卡（正常/异常，首次填写后不可改，管理员修改需留痕）
  → 异常记录一键生成报修单（关联 repair_record_id）
  → 报修结单/完成后自动将巡检记录标记为"已处理"
```

### 7.4 投诉流程

```
任何人提交投诉（类型：投诉/建议/咨询）
  → 管理员受理并指定处理人
  → 处理人处理、管理员回复解决方案
  → 投诉人确认完成并评价
```

## 8. 数据隔离设计

- **业主**：房屋、车位、缴费记录按业主档案过滤；报修、投诉按创建人/业主过滤；
- **维修工**：报修列表只显示待接单工单与自己负责的工单；
- **巡检员**：巡检记录按指定巡检员过滤，未指定任务可抢单；
- **其他角色**：默认全量数据，操作权限由菜单分配控制；
- **设备记录**：对所有登录角色开放（只读汇总，不允许手动增删改）。
